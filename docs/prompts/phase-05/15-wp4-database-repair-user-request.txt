# 戏境AI — Phase 5 WP4 数据库安全修复与最终复验

## 一、任务目标

你现在继续实施「戏境AI」Phase 5 WP4。

WP1、WP2、WP3 已验收通过。WP4 已完成主要启动验证、冷启动安装、资源恢复、网站回归、3D模型测试和比赛排练，但在最终验收前发现两个必须处理的问题：

**问题 A：数据库路径配置错误或现有业务数据库缺失时，程序可能自动创建空数据库。**

**问题 B：Agent数据库损坏可能导致整个应用启动失败，进而影响不依赖该数据库的静态网页和已有3D资产展示。**

本次任务只修复这两个问题，并执行针对性复测及必要的回归测试。

最终目标是：

1. 防止错误配置导致意外创建空业务数据库。
2. 防止数据库损坏时自动重建或覆盖原有数据。
3. 尽可能隔离数据库故障，保留不依赖该数据库的页面及已有资产展示能力。
4. 保留合法的首次初始化流程。
5. 通过真实测试证明修复有效。
6. 更新WP4报告与证据，停止等待人工验收。

**不得借此重构数据库架构，不得进入WP5。**

重点查找：

1. SQLite连接是否在文件不存在时自动创建文件。

## 五、第二阶段：修复数据库路径与初始化安全

### 5.1 明确区分两种运行场景

必须区分：

**场景一：首次安装或显式初始化。**

用户明确执行项目规定的初始化操作，允许按照既有Schema创建数据库和表。

**场景二：已有业务数据库的正常运行。**

系统预期读取现有业务数据库。此时数据库缺失、路径错误或文件不可访问，不得自动创建空数据库来继续运行。

如果项目已有初始化命令、初始化脚本或配置开关，优先复用。

如果当前没有明确区分这两种场景，使用最小改动增加显式初始化入口或配置，不得重建整个数据库管理系统。

### 5.2 数据库路径校验

启动数据库相关服务之前，检查：

- 配置是否存在。
- 路径是否符合当前项目的配置规则。
- 预期数据库文件是否存在。
- 路径指向的是文件还是目录。
- 文件是否可访问。
- 是否误用了临时目录或默认目录。
- 现有数据库是否能正常读取。

对于应当存在的数据库，缺失时必须报出明确的配置错误。

不得静默回退到另一个数据库路径。

不得因为目标目录可写，就直接创建一个空业务数据库。

### 5.3 防止SQLite意外建库

注意：普通SQLite连接可能在文件不存在时创建新文件。

根据项目实际连接方式，采取合适的安全策略，例如先验证现有数据库文件，再使用适当的连接模式打开它。

不能机械地将所有连接都改成只读，因为现有业务功能可能需要合法写入。

要求：

- 正常业务数据库仍能按照既有权限读写。
- 预期存在的数据库缺失时，不自动创建新文件。
- 路径错误时，不在错误位置生成空数据库。
- 显式首次初始化时，仍然可以合法建库。
- 已有数据库的表结构和数据不发生非预期变化。

### 5.4 初始化流程保护

如果当前应用启动时无条件建表，应根据实际架构将合法初始化与普通运行分离。

普通运行不得因为缺少数据库而自动进入初始化流程。

如果首次初始化必须创建数据库，应要求明确的初始化命令、受控配置或项目现有的显式操作。

禁止：

- 每次启动都强制重建数据库。
- 发现表缺失就清空数据库重建。
- 自动使用空数据库覆盖原有业务路径。
- 自动删除损坏文件。
- 把初始化失败转换成初始化成功。

### 5.5 保持兼容性

不要随意改变：

- 现有Schema。
- 历史任务ID。
- Agent事件记录。
- 角色JSON。
- 文化审校结果。
- 已有资产关联。
- WP2历史档案接口协议。

如需修改连接层，应确保正常业务路径的接口行为保持兼容。

## 六、第三阶段：隔离Agent数据库故障

### 6.1 目标

Agent数据库损坏时，应明确提示相关功能不可用，但尽可能保留不依赖该数据库的功能。

不能为了让整个应用看起来正常，而伪装Agent数据库已经恢复。

### 6.2 启动过程

检查FastAPI启动过程中是否存在以下问题：

- Agent数据库校验异常直接抛出并终止整个应用。
- 数据库初始化和静态页面服务耦合。
- 所有路由必须等Agent数据库成功连接后才能注册或响应。
- 健康检查无法区分应用进程正常与数据库服务异常。

在不改变整体架构的前提下，尽量实现必要的故障隔离。

推荐行为：

1. 应用能够注册并提供不依赖数据库的路由。
2. 数据库相关服务启动前进行必要的安全校验。
3. 数据库损坏时，记录明确错误和故障状态。
4. 历史档案、Agent历史查询等依赖该数据库的功能返回可理解的服务不可用提示。
5. 静态文化页面和不依赖该数据库的已有GLB查看能力尽可能保持可用。
6. 健康检查应分别反映应用可用性和Agent数据库可用性。

具体健康检查接口以项目现有实现为准。不要为了实现本任务而新建复杂监控平台。

### 6.3 安全失败

Agent数据库损坏时：

- 不自动创建空Agent数据库。
- 不删除损坏文件。
- 不自动重跑Agent。
- 不自动调用DeepSeek。
- 不自动执行数据库迁移。
- 不覆盖已有角色JSON或文化审校结果。

错误信息应使用安全的中文提示。

服务端日志可以记录必要的诊断信息，但不能泄露API Key、令牌或其他秘密。

如果现有应用架构决定某些功能无法独立运行，应如实报告，不得为了追求完全降级而大规模重构。

### 6.4 恢复流程

在隔离测试副本中验证：

1. 数据库正常时服务正常。
2. 数据库损坏时相关功能明确失败。
3. 不依赖数据库的功能尽可能正常。
4. 将测试配置恢复到有效数据库后，服务能够重新启动或按文档恢复。
5. 恢复过程中不创建第二个意外的空数据库。
6. 原有真实业务数据库不受影响。
