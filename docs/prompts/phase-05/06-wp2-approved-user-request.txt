| Agent执行记录 | 实际数据源 | 实测填写 | 实测填写 | 实测填写 |

| 人工确认记录 | 实际数据源 | 实测填写 | 实测填写 | 实测填写 |

==================================================
四、第二步：设计只读历史查询API
==================================================

如果现有历史数据支持查询，优先复用现有服务与Schema。

根据实际路由规范选择接口名称，不要机械套用固定路径。

建议支持以下能力：

### 1. 历史任务列表

提供只读查询能力，支持：

- 按创建时间倒序排列。
- 分页。
- 按任务状态过滤。
- 按任务类型过滤。
- 按任务ID查询。
- 显示真实任务开始时间、结束时间及状态。
- 显示可确认的任务来源和执行类型。

可展示的状态包括项目实际支持的状态，例如：

- RUNNING
- COMPLETED
- FAILED
- PAUSED
- CANCELLED
- UNKNOWN

必须使用项目真实定义的状态。不存在的状态不要擅自添加到历史数据中。

如果某项状态或时间无法确认，应返回明确的未知值，而不是推断。

### 2. 单个任务详情

如果数据存在，允许查看：

- 任务基本信息。
- Agent执行顺序。
- 每个Agent的名称。
- 输入和输出摘要。
- 执行开始与结束时间。
- 状态及错误摘要。
- RAG引用与来源。
- 角色JSON或已保存结果。
- 文化审校结果。
- 人工确认状态。
- 相关事件时间线。

只展示真实保存的字段。

某个Agent的详细输入、输出或事件如果没有被持久化，必须显示“历史记录未保存该信息”，不能自动重建成看似真实的执行记录。

### 3. 只读安全要求

历史查询API必须是只读的。

禁止：

- 修改历史任务状态。
- 重新执行任务。
- 重新调用Agent。
- 重新生成角色。
- 重新调用RAG生成答案。
- 重新写入文化审校结果。
- 修改人工确认状态。
- 删除历史任务。
- 修改已有角色资产。

优先使用HTTP GET接口。

如果项目已有事件存储或状态管理机制，复用现有读取能力，不得为历史查看而触发新的执行流程。

确保查询不会修改数据库记录、刷新任务状态或触发后台任务。

### 4. 查询边界与性能

根据实际数据量实现合理的分页和结果限制。

不要一次返回全部历史任务及完整大字段。

任务列表优先返回摘要，详细内容按任务ID单独读取。

对不存在的任务返回明确的404或项目统一错误格式。

对数据库异常返回可理解的错误信息，不泄露SQL、文件系统敏感路径或内部密钥。

如果系统支持跨用户或跨会话数据隔离，必须沿用现有访问控制，不得因增加历史查询而扩大数据可见范围。

==================================================
五、第三步：实现Agent历史查看界面
==================================================

优先复用现有AI戏韵工坊及War Room相关界面。

先检查现有导航、卡片、状态标签、时间线和模态窗口，再决定最小改造方式。

不得大改8个HTML页面。

### 1. 历史任务列表

用户应能够看到：

- 任务标题或类型。
- 任务ID。
- 创建时间。
- 当前记录的最终状态。
- 实际执行过的Agent。
- 是否具有完整的历史事件记录。
- 结果是否仍然可读取。

列表应清晰、易读，中文优先。

避免过小字体和过多英文缩写。

### 2. 历史任务详情

用户选择某个任务后，应能查看：

- 任务摘要。
- Agent执行时间线。
- 各Agent真实保存的输入与输出摘要。
- RAG研究来源。
- 角色JSON。
- 文化审校结果。
- 人工确认记录。
- 失败或暂停原因。
- 相关资产关联。

如果某一步只有状态，没有详细输入输出，应如实显示，不要生成补全内容。

### 3. 历史与实时状态明确区分

界面必须显著区分以下三种情况：

**真实历史记录**

来自持久化存储，可以追溯到具体任务或运行记录。

**当前实时执行**

当前确实有任务正在运行，且页面获得了真实的状态更新。

**静态演示或测试数据**

用于测试、展示或开发，不代表真实执行历史。

建议在任务详情上明确显示来源类型。

如果当前页面仅在查看历史记录，不得显示“正在运行”等容易误导用户的状态。

不能将过去的SSE事件重新播放后冒充实时执行。

如果项目已有历史回放功能，可以保留，但必须清楚标记“历史回放”，且不得触发真实Agent调用。

### 4. 加载、空状态与错误状态

至少实现：

- 加载中。
- 有历史记录。
- 无历史记录。
- 任务详情不存在。
- 历史记录不完整。
- API不可用。
- 数据格式异常。
- 用户重新查询后的恢复状态。

错误提示使用清楚的中文。

页面失败后应允许用户重新读取，而不是自动重新执行任务。

### 5. 前端安全

展示历史文本、错误信息和Agent输出时：

- 使用安全的文本渲染方式。
- 不直接将未信任内容插入HTML。
- 不执行历史记录中的脚本。
- 不渲染可执行的用户提供HTML。
- 不暴露API Key、签名URL或其他秘密信息。

如果历史输出包含超长文本，应使用摘要、展开查看或截断机制。

==================================================
六、第四步：保持与已有角色及3D资产的边界
==================================================

WP2的核心是查看历史任务，不是重新生成角色。

如果某个历史任务已经保存角色JSON，允许只读查看。

如果角色JSON关联了已有3D资产，可以提供只读链接或查看入口。

但是：

- 不能根据角色JSON自动触发建模。
- 不能因为某个历史任务没有3D资产就重新生成模型。
- 不能把Q版模型错误关联到写实角色。
- 不能把“绛绣·戏韵”误标为历史真实人物。
- 不能改变已验收的两个GLB。
- 不能修改Neural4D额度。
- 不能恢复已关闭的创建入口。

已有角色与模型的关系必须基于真实资产ID、角色ID或现有数据关联。

如果无法确认对应关系，应显示“未建立关联”。
