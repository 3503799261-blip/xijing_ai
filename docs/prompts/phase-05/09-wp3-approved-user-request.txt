四、工作包A：评委演示导览
==================================================

### 4.1 设计原则

评委不应该先阅读大量技术文档，才能理解作品的核心价值。

打开网站后，应能快速理解：

- 这是一个什么平台。
- 它解决什么问题。
- 京剧私有知识库如何提供文化知识。
- 多Agent如何协同完成角色设计。
- 文化审校和人工确认发挥什么作用。
- 两个已有真实3D模型如何展示。
- 企业模式与普通文化传播模式有什么区别。

重点是帮助评委看懂已有能力，不是增加新的AI功能。

### 4.2 演示导览入口

根据现有首页和工坊布局，选择最合适的入口。

优先考虑：

- AI戏韵工坊中的「比赛演示导览」。
- 清晰的「开始体验」入口。
- 现有功能卡片中的演示顺序提示。

具体实现以现有布局为准，不要为了增加入口破坏原有导航。

导览入口必须使用中文、易读、易发现。

不要将首页改造成完全不同的应用。

### 4.3 推荐的演示步骤

根据真实代码，设计一个简洁的分步导览。

建议流程如下：

**第1步：认识戏境AI**

说明项目目标：通过AI帮助大众理解京剧文化，并探索文化数字资产的创作与展示。

**第2步：体验京剧知识问答**

引导评委提出一个适合现有私有知识库的问题。

如果当前允许使用真实问答，应清楚说明这会产生真实API请求；WP3不得自动发起该请求。

如果当前不具备真实API条件，提供已有真实历史记录的只读查看入口，或明确提示暂不可实时体验。

**第3步：观察多Agent协作**

引导评委查看任务规划、文化研究、角色设计、文化审校和人工确认。

只有在真实执行时才显示实时执行状态。

如果查看历史任务，明确标注为「历史执行记录」。

**第4步：查看角色设计与文化审校**

说明角色JSON、文化审校结果和人工确认的关系。

不得将尚未实现的能力描述成已完成。

**第5步：展示真实3D资产**

引导评委分别查看Q版模型与写实主展示模型「绛绣·戏韵」。

说明它们是此前已经真实生成的两个3D资产，不代表当前页面每次操作都会重新生成模型。

**第6步：认识企业应用方向**

解释企业模式面向游戏角色设计、动漫IP和地方文旅数字角色等场景。

如果没有真实企业客户或实际商业案例，必须标明这是商业应用方向或设计方案，不能伪称已有企业交付成果。

### 4.4 导览交互要求

根据现有技术实现合理选择：

- 分步卡片。
- 简洁的步骤导航。
- 当前步骤高亮。
- 下一步与上一步。
- 跳过导览。
- 退出导览。
- 返回对应真实功能。
- 刷新页面后的合理状态处理。

不要求同时实现所有交互形式。

选择最稳定、改动最少的一种方案。

导览必须能够退出，不得遮挡整个网站而无法恢复。

不得强制用户依次点击所有步骤才能使用其他功能。

不得把导览步骤完成状态误当作AI任务完成状态。

### 4.5 视觉要求

遵循网站现有的酒红、金色、米白等视觉体系。

要求：

- 中文优先。
- 关键文案适合投影观看。
- 步骤层级清晰。
- 主按钮和次按钮有明显区别。
- 手机窄屏下不出现严重溢出。
- 保留现有网站的文化风格。
- 不引入过多动画或影响演示稳定性的视觉效果。

五、工作包B：核心操作路径清晰化
==================================================

本工作包只调整必要的界面说明、入口和状态提示，不重新实现已有业务逻辑。

### 5.1 京剧RAG问答

检查问答界面是否清楚说明：

- 可以向AI提问哪些内容。
- 回答会依据知识库检索结果生成。
- 引用可以查看真实资料来源。
- 当资料不足时，系统应明确说明。
- 外部API不可用时，系统不会保证实时生成成功。

如现有功能已经具备这些能力，只改善文案和入口即可。

不得为了展示效果增加伪造引用。

### 5.2 Agent工作流

让用户更容易理解工作顺序：

任务规划
→ RAG文化研究
→ 角色设计
→ 文化审校
→ 人工确认。

该顺序仅作为当前工作流的说明；具体节点、条件分支和错误状态必须以实际实现为准。

区分：

- 实时执行。
- 历史任务查看。
- 历史回放。
- 静态说明。

如果项目不支持某种状态，不得在界面中将其表现为已实现能力。

### 5.3 角色与3D资产

清楚说明三个不同概念：

1. 角色创作方案。
2. 已保存的角色JSON。
3. 已生成并保存的3D模型资产。

它们不能被自动视为同一件事。

只有真实存在关联记录时，才展示角色与模型的关联。

如果当前角色尚未生成对应3D模型，应显示清晰提示，不得自动触发生成。

### 5.4 企业模式

保持企业模式的现有入口和布局。

如果当前企业模式主要是需求入口或概念流程，应明确说明其当前能力边界。

不要在本工作包中扩展完整企业订单、项目管理、客户管理或商业交付系统。

==================================================
六、工作包C：异常状态与降级处理
==================================================

目标是：当API、网络或私有资源不可用时，用户能理解发生了什么，并且有安全、诚实的下一步选择。

### 6.1 统一异常状态

检查现有前端与后端的错误处理。

优先复用现有状态组件和错误格式。

必要时补齐以下状态：

- 正在加载。
- 请求成功。
- 请求超时。
- 网络断开。
- 服务不可用。
- 认证失败。
- 请求受限。
- 私有资源缺失。
- 返回内容异常。
- 暂无历史记录。
- 结果不完整。
- 用户可以重新尝试。

只显示实际可确定的状态。

不要将所有错误都简单显示成「AI出错了」。

对于无法确定根因的错误，显示「请求暂时未能完成」等中性提示。

### 6.2 API失败时的行为

发生失败时：

1. 保留用户已经输入的内容。
2. 停止当前界面上的等待状态。
3. 展示明确的中文提示。
4. 允许用户手动重试。
5. 不自动重新发送付费请求。
6. 不自动重跑Agent。
7. 不自动跳转到模型创建。
8. 不将失败结果包装为成功。

如果现有请求存在自动重试机制，先检查其风险与费用影响，再进行最小必要调整。

不得擅自修改所有业务接口的重试策略。

### 6.3 私有模型或本地资产缺失

如果RAG模型、向量数据库、GLB或纹理资源缺失：

- 显示具体缺少的资源类别。
- 告知用户哪些功能暂时不可用。
- 给出合理的配置或恢复建议。
- 保持其他可用页面正常工作。
- 不因为单一资产缺失导致整个工坊无法访问。

不得泄露本机敏感路径、API Key或私有令牌。

不得将资源缺失伪装成模型正在生成。

### 6.4 浏览器加载失败

对于现有3D Viewer：

- 保留已经实现的加载和错误状态。
- 如果模型无法加载，提供明确错误提示。
- 允许用户重新加载现有资产。
- 重新加载只允许获取已经存在的模型文件。
- 禁止重新调用Neural4D。
- 禁止重新生成模型。
- 不修改已经验收的GLB。

### 6.5 降级原则

采用以下优先级：

第一优先级：当前真实功能正常使用。

第二优先级：如果实时服务失败，提供明确的失败提示。

第三优先级：用户可以主动选择查看已有的真实历史任务或已保存结果。

第四优先级：如果没有可用的历史记录，则展示空状态和下一步建议。

**禁止在API失败后悄悄切换到假答案。**

如果系统提供预设演示内容，必须明确标注为静态演示内容，不能伪装成实时生成结果。

==================================================
十、修改范围与代码质量
==================================================

本工作包优先修改：

- AI戏韵工坊相关HTML。
- 对应独立CSS。
- 对应原生JavaScript。
- 必要的现有错误处理。
- 导览相关文档。
- 测试代码与测试报告。

以上为候选范围，不代表所有文件都必须修改。

必须根据实际代码确定最小文件清单。

CSS使用现有命名规范，并尽量使用工坊专属前缀。

JavaScript尽量沿用现有模块结构。

不要引入全局变量污染。

不要重复实现已有的历史查询、模型查看或Agent功能。

不要改变RAG检索策略、Agent提示词、角色生成逻辑、Neural4D资产结构。

如果发现需要大规模修改后端架构才能实现某项体验，先记录为后续建议，不得擅自扩展WP3。

==================================================
十一、Git与Prompt记录
==================================================

开始修改前记录：

- 当前分支。
- 当前HEAD。
- 工作区状态。
- 允许修改的文件范围。

修改后检查：

- git diff。
- 修改文件清单。
- 是否包含不相关文件。
- 是否泄露敏感信息。
- 两个GLB文件Hash是否保持不变。
- WP1与WP2提交是否保留。
- Neural4D创建锁是否仍然有效。

采用细粒度本地提交。

建议提交类型：

`feat(phase5): add guided demo and graceful fallback`

测试证据及阶段报告可以独立提交。

更新：

`docs/prompts/phase-05/README.md`

记录：

- WP3实际执行Prompt。
- 实际实现范围。
- 测试结果。
- 失败和修复记录。
- Git提交记录。
- 未解决的问题。
- WP3最终状态。

禁止：

- git push。
- 合并main。
- 重写历史。
- 删除用户分支。
- 覆盖WP1或WP2历史报告。
- 将API密钥提交至Git。
- 将私有模型文件或大型资产意外加入提交。

如果工作区出现无法归属的修改，停止并报告。

==================================================
十三、WP3验收标准
==================================================

完成后逐项核对：

[ ] 评委能够找到清晰的演示入口。

[ ] 导览步骤与真实功能一致。

[ ] 能够从导览进入RAG、Agent历史与3D展示等真实功能。

[ ] 实时执行、历史记录和静态演示有清晰区分。

[ ] API失败时不会自动产生额外付费调用。

[ ] API失败后用户能够看到明确提示。

[ ] 已有历史记录可以作为只读备用演示素材。

[ ] 没有历史记录时显示真实空状态。

[ ] 私有资源缺失时能够清楚提示。

[ ] 3D模型加载失败时可恢复。

[ ] 没有伪造Agent执行状态、引用或商业案例。

[ ] 导览不会破坏原有8页网站。

[ ] 桌面与手机窄屏检查已执行。

[ ] 相关后端与前端测试已执行。

[ ] 测试报告与Prompt记录已更新。

[ ] Git修改可追溯。

[ ] 工作区状态已核对。

[ ] 本轮未调用付费API。

[ ] 本轮未调用Neural4D创建接口。

[ ] 两个GLB未被修改。

[ ] 未开始WP4。

如果某项未满足，必须在最终报告中标注，不得将其描述为通过。
