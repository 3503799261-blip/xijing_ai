# 戏境 AI 前端产品化改造：AI戏韵工坊与全站导航优化

你现在负责对当前 VS Code 打开的「戏境 AI」项目进行一次前端产品化改造。

这次不是重新开发项目，而是在保留现有功能、数据和技术架构的前提下，减少界面复杂度，去掉开发测试痕迹，并优化 AI 戏韵工坊的问答体验。

请先审查现有代码，再直接实施修改、运行测试并交付报告，不要只提供设计建议。

## 一、改造目标

重点解决三个问题：

1. AI 戏韵工坊功能区过多、信息层级混乱，普通用户难以理解。
2. 页面中存在开发测试提示、调试信息、临时状态说明及原型式功能卡片，不像完整产品。
3. 全站导航栏过宽，需要适当收窄；AI 问答区需要改为类似 ChatGPT 的上下文对话布局。

整体设计方向：**简洁、专业、文化感、低 AI 味、比赛演示友好。**

不要为了体现 AI 而堆叠大量发光效果、渐变卡片、AI 图标、复杂动画或技术术语。优先保证清晰、自然、易用。

## 二、第一项：AI 戏韵工坊整体简化

先检查 `about.html`、相关 CSS、JavaScript，以及工坊调用的真实后端接口。

重新梳理现有功能，将普通用户真正需要的操作放在主要区域。

### 主界面只突出以下内容

- 京剧知识问答。
- 上下文连续对话。
- 回答中的知识库引用与来源。
- 新建对话和历史会话。
- 必要的加载状态、错误提示和重试操作。

多 Agent 角色创作、文化审校、人工确认、角色 JSON、已有 3D 模型及企业模式等现有能力，不得直接删除或破坏。

请根据现有真实功能，合理地将它们放入次级入口、独立页面或折叠区域，避免所有功能同时挤在工坊首页。

如果某项功能尚未真正接入，只能如实标注为尚未开放，或在不破坏现有流程的前提下从主要操作区移除；不得把未实现的功能包装成已经可用。

### 清理开发测试痕迹

检查并处理面向开发者的内容，例如：

- 测试专用说明、模拟数据提示及调试文案。
- 内部接口、开发状态、测试模式等非用户必需的信息。
- 重复的功能卡片、重复按钮、冗长技术说明。
- 让用户误以为产品尚未完成的临时占位内容。

注意：只清理用户界面中的开发测试痕迹，不得删除必要的开发日志、测试代码、历史报告、故障记录和安全机制。

## 三、第二项：问答区改成 ChatGPT 式上下文对话

这是本次改造的核心。

请将 AI 戏韵工坊的问答模块重构为三部分布局。

### 左侧：历史会话栏

占据较窄的固定或可折叠区域，包含：

- 新建对话按钮。
- 历史会话列表。
- 会话标题及必要的时间信息。
- 切换已有会话。
- 继续之前的上下文。
- 必要的空状态和加载状态。

历史记录必须使用现有后端和真实持久化数据，不能只用静态示例。

切换会话时，正确恢复该会话已有的消息。新建对话时，应创建独立的上下文，不能把上一个会话的内容混入新会话。

如果现有接口已经支持历史分页、筛选或详情读取，应优先复用。

### 中间及右侧：主要问答区域

主要空间用于当前对话，采用自然的上下文聊天布局。

- 用户消息与 AI 回答按照时间顺序上下排列。
- 用户问题与 AI 回答在视觉上有清楚的区分。
- 长回答具有舒适的阅读宽度和行距。
- 支持连续追问，前一轮对话在当前会话中保留。
- AI 回答中的 RAG 引用应清晰展示，用户能够查看资料来源。
- 加载中、无结果、资料不足、网络错误和服务不可用时，均应有明确且友好的提示。
- 发送失败时，允许合理重试，不要丢失用户已经输入的内容。

问答页面不要再用大量并列卡片展示技术模块。让用户一进入页面就知道：**在这里提问，获得回答，并可以继续追问。**

### 底部：固定或稳定的输入区

参考 ChatGPT 的交互方式，设置清晰的消息输入框和发送按钮。

要求：

- 输入框支持多行文字。
- 发送后显示用户问题，并在原会话中呈现 AI 回复。
- 请求期间明确显示正在生成或正在检索。
- 支持合理的键盘交互。
- 页面滚动时，输入区位置稳定，不遮挡对话内容。
- 不要在输入框周围堆放大量次要按钮和技术说明。

可以参考 ChatGPT 的信息架构与交互逻辑，但不要照搬其品牌标识、商标或具体视觉资产。

### 重要的后端约束

必须继续使用现有 DeepSeek、RAG 和 FastAPI 接口。

先查清当前会话、消息历史和问答接口的数据结构，再决定如何适配。

如果后端尚未提供完整的多轮会话能力，应先评估最小改造方案。不得只把消息显示在前端，却没有正确传递上下文。

必须保留：

- 真实 DeepSeek 问答。
- 现有 RAG 检索与来源引用。
- 正确的会话隔离。
- 现有历史档案及 Agent 任务记录。
- 现有鉴权、错误处理和安全降级逻辑。

不要把 Agent 历史档案与普通聊天历史混为一谈。二者可以在产品中合理衔接，但必须保留各自的数据含义。

## 四、第三项：全站导航栏适当收窄

检查全部 8 个原有 HTML 页面及其共用导航样式。

将导航栏宽度适当缩小，目标是比当前明显紧凑一些，但不影响可读性。

具体要求：

- 优先修改共用 CSS，避免逐页产生不同的导航尺寸。
- 适当减少导航项之间的间距及不必要的左右留白。
- 保留原有导航文字、页面入口、功能和文化内容。
- 不要为了缩窄而强行截断文字。
- 桌面端保持整洁，平板与手机端继续使用合理的响应式布局。
- 导航调整之外，其他页面布局保持不变。

请先根据现有实际宽度和截图做小幅调整，不要自行大幅重做全站视觉设计。

## 五、第四项：整体视觉规范

保持京剧文化网站的原有气质，减少机械化的 AI 产品视觉。

推荐方向：

- 以现有页面的背景和品牌色为基础。
- 通过留白、字体层级、细分隔线和清晰的布局建立秩序。
- 少用大面积高饱和渐变和发光边框。
- 避免每个模块都做成独立的圆角卡片。
- 统一按钮、输入框、标题和状态提示的视觉规范。
- 让回答、引用和会话历史成为视觉重点，而不是装饰性组件。
- 保持桌面端空间利用率高，避免文字太小。

不要随意改变京剧文化页面的原有图片、文章、音乐、视频、角色介绍或画廊内容。

## 六、第五项：真实测试

完成后必须进行实际验证，不能只根据代码修改结果宣布通过。

至少验证：

1. 全站 8 个原有页面正常打开。
2. 导航栏在桌面、平板和手机视口中正常显示。
3. 新建会话能够正常提问。
4. DeepSeek 能返回真实回答。
5. 连续追问能够保持当前会话的上下文。
6. 切换历史会话能够恢复正确消息。
7. 不同会话之间没有上下文串线。
8. RAG 引用和来源能够正常显示。
9. 加载、错误、资料不足和重试状态正确。
10. 输入框在长对话及移动端布局中正常工作。
11. 多 Agent、Agent 历史、文化审校、资产页面和两个真实 GLB 的原有功能没有回归问题。

优先使用现有测试和浏览器自动化工具。

禁止为了测试而自动调用付费模型。如果需要真实 DeepSeek 调用，请先使用已有本地测试证据；确实无法验证时，停止并说明需要的调用次数与预计费用，等待授权。

绝对禁止调用 Neural4D 或创建任何新的建模任务。

不得初始化、清空或重建 SQLite、Qdrant、BGE 或其他现有业务资源，不得修改 `.env` 或泄露 API Key。

## 七、第六项：开发纪律与交付

开始前先记录当前 Git 分支、HEAD 和工作区状态，检查是否存在用户未提交的修改。

按最小改动原则实施，保留现有功能和资源。

完成后：

- 更新必要的测试。
- 保存修改前后的截图及测试证据。
- 记录实际修改文件和测试结果。
- 将本次 Prompt 与执行记录保存到 `docs/prompts/` 的适当目录。
- 生成中文阶段报告，建议路径为 `docs/reports/frontend-productization.md`。
- 按逻辑拆分 Git 提交。
- 工作区存在用户修改时，不得擅自覆盖或提交无关内容。
- 不得擅自切换分支、合并分支或推送 GitHub。

最终报告应明确区分已通过、失败和未执行的测试，不得编造结果。
