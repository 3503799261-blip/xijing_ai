## 二、Phase 5 总目标

本阶段的目标是将已有功能整理成一套可稳定演示、可复现、可向评委清晰讲解的比赛作品。

重点不在于增加功能数量，而在于证明：

1. 京剧私有知识库能够提供有来源依据的文化知识。
2. 多Agent能够围绕用户需求开展可观察的协作。
3. 系统能够将角色设计、文化审校和人工确认串联起来。
4. 两个真实3D模型能够在网页中稳定展示和交互。
5. 个人非遗传播模式与企业数字角色设计模式具有明确区别。
6. 项目能够在评委演示环境中启动、运行并展示真实成果。
7. 关键能力有可核验的测试、日志、报告或其他证据支撑。

所有演示必须以实际实现为依据。

不得将静态页面描述为真实AI功能，不得将历史回放描述为实时Agent执行，不得将模拟结果描述为真实模型生成。

## 三、严格执行检查点 A：先审查，后停止

当前只执行Phase 5检查点A。

首先审查仓库，不进行正式功能开发。

### 1. 检查Git与项目结构

确认：

- 当前仓库路径。
- 当前分支与HEAD。
- 工作区是否干净。
- Phase 1至Phase 4的提交历史是否完整。
- 两个真实GLB资产的实际存储位置。
- RAG、Agent、Viewer、企业模式的实际入口。
- 当前启动方式和环境变量配置。
- 是否存在未提交的用户修改。

禁止重置、覆盖、清理或删除用户已有文件。

### 2. 审查所有阶段报告

优先查阅实际存在的文件，包括但不限于：

- `docs/reports/phase-01.md`
- `docs/reports/phase-02.md`
- `docs/reports/phase-03.md`
- `docs/reports/phase-04.md`
- `docs/reports/phase-04-final-acceptance.md`
- `docs/evidence/test-results/`
- `docs/prompts/`

若文件名或目录与上述示例不同，以实际仓库为准。

必须识别：

- 已经完成的能力。
- 现有测试的真实覆盖范围。
- 已知缺陷。
- 尚未验证的事项。
- 当前演示流程中可能出现的断点。
- 各阶段之间尚未形成闭环的功能。

不能因为测试数量很多就直接认定所有比赛要求已经满足。

### 3. 审查比赛评审标准

从现有项目文件、用户已提供的比赛要求及可访问的官方比赛资料中提取真实评审维度。

优先核对：

- 创新性。
- AI技术应用深度。
- 产品完整度。
- 用户体验。
- 实际应用价值。
- 商业落地潜力。
- 作品演示和提交材料要求。

不得编造评分比例、截止时间、提交格式或官方规定。

如果无法找到某项正式要求，明确标注「待用户确认」，不要猜测。

### 4. 进行现状差距分析

重点分析以下问题：

#### A. 用户主流程

能否完整演示：

用户提出京剧文化或角色设计需求
→ RAG文化研究
→ 多Agent协作
→ 角色方案与文化审校
→ 人工确认
→ 选择已有3D资产进行展示。

如果任何步骤只是界面占位、手动操作或历史回放，必须明确标注。

#### B. RAG可靠性

检查：

- 回答是否可以追溯到真实资料。
- 引用是否能够对应实际来源。
- 资料不足时是否正确拒答。
- API异常时是否有清晰提示。
- 演示是否依赖外网和API密钥。

#### C. Agent可观察性

检查：

- 用户能否看出当前执行到哪个Agent。
- 各Agent的输入、输出、状态和交接是否清楚。
- 文化审校和人工确认是否真正参与流程。
- 失败、暂停、冲突是否有明确反馈。
- 历史回放是否与实时执行区分。

#### D. 3D Viewer

检查：

- 两个真实模型能否稳定加载。
- 旋转、缩放、重置是否有效。
- Loading、Ready、Error状态是否真实。
- 资产缺失或加载失败时是否可以恢复。
- 是否有模型来源和资产状态说明。

实体手机触摸测试尚未完成，不能将模拟测试结果写成实体设备通过。

#### E. 企业模式

检查：

- 企业模式入口是否真实可用。
- 是否能清楚展示企业用户的目标和流程。
- 是否复用了已有角色设计与3D资产能力。
- 哪些能力已经接入，哪些仍是规划或演示。
- 是否存在与个人模式重复、但没有商业价值说明的界面。

#### F. 比赛演示风险

检查：

- 启动步骤是否过于复杂。
- 是否依赖开发者本机路径。
- 是否依赖未配置的API密钥。
- 是否需要下载模型或外部资源。
- 是否有网络中断、API限流、超时等风险。
- 是否有不依赖付费API的演示备选方案。

## 四、提出Phase 5实施方案

完成审查后，形成正式实施建议。

建议优先评估以下工作包，但不得在未审查现状前假定它们全部需要开发。

### Work Package A：端到端演示流程

形成一条完整、连贯、可在评委面前重复执行的主流程。

优先使用已有真实能力和已有两个3D模型，不新增模型生成任务。

明确每一步的：

- 操作入口。
- 输入内容。
- 实际处理逻辑。
- 页面反馈。
- 预期结果。
- 失败处理。
- 可留存的验收证据。

### Work Package B：Agent过程可视化

评估如何让评委直观看到Agent之间的协作过程。

优先复用现有功能。

只有在审查发现确实存在断点时，才提出最小必要修改。

不得为视觉效果伪造Agent状态、执行日志或决策结果。

### Work Package C：比赛演示模式

评估是否需要提供清晰的演示入口或引导。

要求：

- 中文优先。
- 关键文字在投影环境中易读。
- 核心功能入口明确。
- 主流程尽量减少无关操作。
- 实时执行、历史回放和预设演示数据明确区分。
- 网络或API不可用时提供诚实的降级提示。

不要为了增加演示模式而重复实现已有能力。

### Work Package D：测试与运行稳定性

设计最终回归方案，覆盖：

- 后端单元与集成测试。
- RAG真实数据与引用检查。
- Agent工作流。
- 前端8页回归。
- 桌面与手机视口。
- 两个真实GLB加载与交互。
- API异常与恢复。
- 配置缺失时的提示。
- 启动和关闭流程。

只有实际执行并记录的测试才能标记通过。

### Work Package E：比赛交付材料

检查是否需要准备：

- 项目介绍。
- 技术架构图。
- 功能流程图。
- 关键创新点说明。
- 真实模型生成证据。
- 测试报告。
- 运行指南。
- 演示脚本。
- 演示失败备用流程。
- 评委常见问题及回答。
- 最终提交检查清单。

先根据正式比赛要求决定交付物，不得擅自假定所有材料都是强制要求。
