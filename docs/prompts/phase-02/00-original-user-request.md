# 五、任务B：RAG技术方案选择

必须比较至少两种可实际部署的技术方案。

## 方案A：轻量RAG（优先考虑）

建议技术：

- Python FastAPI
- SQLite保存资料与来源元数据
- Chroma或Qdrant本地持久化模式作为向量数据库
- 中文Embedding模型
- DeepSeek或其他用户可用的LLM API
- 必要时加入轻量关键词检索
- 原生JavaScript通过Fetch调用后端

优势：

- 适合单人开发；
- 工程复杂度较低；
- 不必部署大量独立服务；
- 方便本地运行；
- 比较容易制作10分钟复现指南。

## 方案B：独立向量数据库服务

可考虑：

- FastAPI
- PostgreSQL
- Qdrant服务
- Embedding模型
- Reranker
- LLM API

必须综合比较：

1. 一周总开发周期；
2. 当前只有HTML/CSS/JS前端的实际情况；
3. Windows本地开发环境；
4. 模型接口的实际可用性；
5. 中文京剧专业名词检索质量；
6. 依赖安装和运行时间；
7. 测试与调试难度；
8. 未来Phase 3多Agent调用方式；
9. GitHub代码复现成本；
10. 本地数据隐私与外部API数据边界。

**建议优先选择轻量RAG，但最终以实际测试和技术分析为准。**

# 八、任务E：实现知识入库处理

本阶段必须实现真实、可重复运行的资料入库流程。

建议流程：

```text
原始资料
   ↓
资料来源与许可检查
   ↓
文本解析
   ↓
内容清洗
   ↓
文档分块
   ↓
元数据关联
   ↓
Embedding向量化
   ↓
向量数据库持久化
   ↓
检索质量检查
```

## 必须实现

1. 能读取本阶段实际采用的知识资料格式。
2. 能识别并剔除无效或重复内容。
3. 能按照章节和语义边界合理分块。
4. 能生成真实Embedding向量。
5. 能将向量及关联ID写入持久化存储。
6. 重复执行入库时不会无限生成重复数据。
7. 文档内容更新后能够重建相关索引。
8. 能通过ID找回对应的原始知识片段。
9. 能记录本次入库数量、失败数量与错误原因。
10. 能在新环境中通过明确的命令重新构建索引。

建议创建独立的入库脚本。

初始分块参数可以采用约300～600汉字、相邻分块重叠60～100汉字，但要根据真实检索效果调整。

不允许只实现假数据插入、关键词硬匹配后宣称已经完成向量化。

# 九、任务F：实现真正的RAG检索系统

这是Phase 2的核心技术任务。

## 1. 检索流程

用户提问后，应完成：

1. 输入校验；
2. 问题Embedding；
3. 向量相似度检索；
4. 必要的关键词匹配；
5. 检索结果排序；
6. 依据阈值或排序结果筛选证据；
7. 返回真实知识片段；
8. 将证据交给大语言模型生成答案。

如果检索质量允许，可以增加混合检索。

但不要为了使用复杂技术而增加不必要的系统依赖。

## 2. 证据溯源

每一条检索结果必须包含：

- 对应文档；
- 实际知识片段；
- 来源ID；
- 章节或定位信息；
- 来源URL（如果存在）；
- 实际检索分数或排序信息。

没有真实文献支持的内容不能生成虚构引用。

## 3. 资料不足处理

对于知识库没有覆盖的问题，例如：

“京剧历史上某个不存在的人物有哪些代表作？”

系统应当识别资料不足的情况。

要求：

- 不编造来源；
- 不生成虚假的确定性回答；
- 清楚告知目前资料不足；
- 可提示用户调整提问方向。

资料不足时必须有明确状态，而不是所有问题都强制给出一个答案。

## 4. 未来Agent复用能力

检索服务必须能够独立调用。

不能将RAG检索逻辑完全写死在聊天接口中。

Phase 3的“京剧研究Agent”应能够直接调用同一套真实RAG检索服务，获取结构化文化证据。

因此，应将以下两种能力分离：

**知识检索服务：返回文献证据。**

**AI问答服务：基于证据生成面向用户的解释。**
