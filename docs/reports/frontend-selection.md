## 1. 最终推荐

推荐 **方案 A：保留 HTML＋CSS，新增模块化原生 JavaScript**。

保留现有多页站点和全部资源，在 `about.html` 原地建立 AI 戏韵工坊。其他七页仅同步关联导航与入口文案。新样式与脚本只加载到工坊页面。不引入 React/Vue/Next，不迁移首页、不新增 SPA 路由、不在 Phase 1 安装 3D 或 AI SDK。

选择依据：本阶段真实交互是四个区域的切换、推荐问题填入、输入校验、Agent 说明展开和待接入反馈。这些交互用小规模原生 JS 即可完成。后续 API、流式状态和模型查看可以独立接入；采用框架也不会自动提供真实 RAG 或 Agent 能力。

主要代价：需要保持状态、DOM 渲染和服务边界，避免脚本变成一整块。浏览器 ES module 应使用 HTTP 运行，因此不能把双击 HTML 作为工坊唯一启动方法。目前本机 HTTP 浏览器预览存在连接限制，必须在实施时先恢复运行与截图条件。

## 2. 四种方案比较

以下时间与风险是依据当前代码范围的工程判断，不是已执行的工期数据或承诺。React/Vue 按“仅局部工坊挂载＋Vite”比较，而非全站迁移。

| 维度 | A 原生 HTML/CSS/JS | B 局部 React＋Vite | C 局部 Vue 3＋Vite | D Next.js |
|---|---|---|---|---|
| 对原网页侵入 | 最低，主体只替换 about | 低至中，新增挂载区和构建入口 | 低至中，新增挂载区和构建入口 | 本项目若整体采用则较高，需新路由/入口组织 |
| 开发时间 | 本阶段最短 | 增加依赖、构建、资产路径验证 | 增加依赖、构建、资产路径验证 | 需要较多迁移和部署验证 |
| 动态交互 | 足够完成全部 Phase 1 要求 | 适合复杂组件/会话状态 | 适合响应式模板/表单状态 | 支持丰富交互，当前服务端能力无明确用途 |
| Agent 状态展示 | 有限状态对象＋渲染函数 | 组件和状态管理更方便扩展 | 响应式状态与组件更方便扩展 | 仍需客户端状态实现 |
| 后续 RAG 对接 | 服务适配层 fetch，后续真实事件流 | 易对接，同样需要真实 API 和引用契约 | 易对接，同样需要真实 API 和引用契约 | 可对接，但与计划的 FastAPI 边界需另定 |
| 后续 3D 展示 | 可接独立 Web 组件或 Three.js，无框架前置要求 | 可选 React Three Fiber/其他查看器 | 可接 Three.js 或 Vue 封装 | 交互模型仍需客户端展示 |
| 维护成本 | 当前最低；复杂度增长后需严格模块边界 | 依赖及构建维护增加，复杂 UI 组织更便利 | 依赖及构建维护增加，复杂 UI 组织更便利 | 对当前小站的维护面最大 |
| 构建与部署 | 无前端构建；静态 HTTP 即可 | 新增 Node、包锁、构建产物、多页资源配置 | 同左 | 增加框架运行/静态导出约束 |
| 一周比赛风险 | 最低，复用既有页面与素材 | 中，收益要与新增验证成本平衡 | 中，收益要与新增验证成本平衡 | 高，目前缺乏 SSR/复杂路由必要性 |

核查过的官方资料：React 明确支持在现有 HTML 的指定节点局部渲染，保留其他内容，因此 B 是可行候选。[React：Add React to an Existing Project](https://react.dev/learn/add-react-to-an-existing-project)

Vue 支持渐进使用、独立脚本及嵌入组件，因此也不必全站迁移；本题 C 包含 Vite，会额外引入构建步骤。[Vue：Ways of Using Vue](https://vuejs.org/guide/extras/ways-of-using-vue.html)

Vite 提供开发服务与生产构建，并需要受支持的 Node 环境；这些是原项目当前没有的运行与交付环节。[Vite：Getting Started](https://vite.dev/guide/)

Next 的官方起步路径基于 React 与 App Router。结合本项目没有 SSR 或复杂路由需求，当前不推荐引入是项目判断，而不是认为 Next 不支持静态网站。[Next.js：Getting Started](https://nextjs.org/docs/app/getting-started)

若以后出现多会话、复杂方案编辑、大量跨组件状态或明确采用 React Three Fiber，再在经用户确认的新阶段中考虑只迁移工坊根节点。状态/接口契约与原七页可保留，但 UI 渲染要重写，迁移不是零成本。

## 4. 前端交互、视觉与易用性

- 总览、问答、Agent、创作各有明确内部导航；进入后更新当前项，管理焦点与地址锚点，浏览器返回行为一并验证。
- 入口按钮、推荐问题、提交和折叠全部可键盘操作；表单有标签，通知使用合适的 live region，错误对应到输入。
- 输入先 trim，校验空白及明确的长度上限，不将用户输入以未经处理的 innerHTML 插入。
- 保留原公共色彩变量、字体和页头页脚。新增类用 `ai-workshop-*`，选择器限定工坊根节点；不新增裸元素或全局 `.card/.btn/.grid/.module` 覆盖。
- 双入口桌面双栏、手机单栏；Agent 卡 4→2→1 列；输入和操作按钮在窄屏可换行。减少动画规则覆盖新增过渡。
- 3D 容器使用真实空态文字；图片示意如果以后使用，必须显式标注“功能预览”，不能宣称可交互模型。
- 原文化内容和素材不扩写、不压缩、不改名。首页导航若实际回归，再作最小范围修复。

## 5. 后续接口扩展边界（本阶段只做前端约定）

建议三个小模块，避免复杂架构：

```text
about.html
  └── js/ai-workshop/main.js       # 事件、面板、表单、状态渲染
        ├── contracts.js           # 状态枚举 + JSDoc 数据约定
        └── services.js            # 明确 unavailable 的服务边界
```

| 数据约定 | 必要字段与用途 |
|---|---|
| ServiceAvailability | capability、available、reason；本阶段所有AI服务 available=false |
| ChatMessage | id、role、content；区分用户消息和服务通知，未来才增加真实assistant数据 |
| Citation | sourceId、title、locator、excerpt；来源于未来真实检索结果，当前空态 |
| AgentState | pending/running/completed/failed/awaiting_confirmation，对应五种指定状态 |
| WorkflowEvent | runId、sequence、agentId、status、summary、progress；未来接受真实事件并处理顺序与失败 |
| CreationDraft | brief、style；仅用户页面内输入，无AI生成含义 |
| ModelTask | taskId、status、progress、previewUrl、downloadUrl；未接入状态无taskId、无虚假百分比 |

Phase 1 的服务适配方法只提供“未接入”的能力结果与说明，不能返回假回答、假文献、假 Agent 执行摘要或模型 URL。不创建 FastAPI 服务、RAG 索引、LLM 请求、SSE 服务、图生3D轮询或微服务。

未来由前端适配层访问本项目后端，后端持有第三方密钥；浏览器仅保存公开的后端基础地址，不能把大模型/Neural4D 密钥放入 JS、HTML 或前端环境变量。流协议、具体 URL、引用定位格式和模型格式在对应阶段结合真实服务确定，当前不冒充已存在的 API。
